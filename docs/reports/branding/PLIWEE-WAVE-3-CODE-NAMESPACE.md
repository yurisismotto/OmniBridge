## 1. Scope

This wave renamed developer-only names, as the plan specifies:

- Rust crates and library targets;
- Rust module paths;
- the protobuf package, its directory and its `java_package`;
- Kotlin *type* names and Android resource *names*;
- log tags, the X11 atom, the clipboard thread name and the temporary-file prefix;
- the Gradle root project name.

**No persistent, installed or wire identifier moved.**

**Explicitly not touched, as the plan requires:**

- `[[bin]] name` and every binary name (W7);
- the Kotlin **package**, `namespace`, `applicationId` and manifest components (W6);
- `APP_ID`, the D-Bus name, the gresource and the icon names (W7);
- every path (W4);
- every wire constant (W5);
- the frozen brand masters and every asset filename (W0/W6/W7);
- historical documents (ADR-0020 D7);
- ADR-0001…0019.

### 2.3 Decisions on ambiguous names

- **`omnibridge-gui` is both the old crate name and the binary name.** Hits that mean the *crate* were renamed: `cargo -p`, "depends on", "links against", "`APP_ID` in …". Hits that mean the *executable or process* were kept for W7: argv in `Launch::parse` tests, `Exec=`, "started by the bus", `Command::new`.
- **The GUI's `eprintln!("omnibridge-gui: …")` prefix is kept.** The [Wave 1 report](PLIWEE-WAVE-1-BRAND-COPY.md) filed it under W3. It is the program-name prefix of stderr messages, which names the binary the user ran, so it moves with the binary in W7. The plan's §2 row for W3 does not list it.
- **The TLS SNI placeholder `omnibridge.invalid` is kept.** It is sent in the ClientHello, so it is on the wire (W5). `security_certification.rs` asserts its bytes.

## 3. Log tags and their harnesses — renamed together

The plan forbids renaming a log tag without renaming, in the same change, every harness pattern that looks for it.

| Renamed name | Producer | Consumers renamed with it |
| --- | --- | --- |
| tracing target `pliwee_capability_notifications` (was `omnibridge_…`) | the crate rename itself | `security-log-evidence.sh` L16 anchor (`grep` on a here-string; not a pipe) |
| tracing prefix `pliwee_` | the crate renames | `file_log_privacy.rs`, `notification_log_privacy.rs` non-vacuity anchors |
| `PliweeFixture` | `FixtureActivity.TAG` | `security-log-evidence.sh` L16 window anchor; `android/fixture/README.md` |
| `PliweeListener`, `PliweeApp` | `OmniBridgeNotificationListener.TAG`, `PliweeApp.TAG` | `NotificationLoggingCanaryTest.TAGS` |
| `PliweeHarness`, `PliweeClipTest` | instrumented harnesses | only their own `adb logcat -s` doc comment; no script greps them |

G3 E proves that no file under `packaging/`, `android/`, `desktop/` or `.github/` still looks for `omnibridge_capability_notifications` or `OmniBridgeFixture`.

**"The anchor is found before any absence claim" (plan, Regression):**

- **L16:** `security-log-evidence.sh` already `abort`s if the tracing anchor or the fixture line is missing from its window. The renamed patterns sit in those same abort branches.
- **Canary test:** `NotificationLoggingCanaryTest` only asserted `captured.isNotBlank()`. `logcat -d` prints `--------- beginning of main` even when no tag in the filter wrote a line, so a stale tag after a rename would have left that check green over an empty capture. The test now also requires **at least one line attributed to one of `TAGS`** before any canary's absence is accepted. That strengthens the test and weakens nothing. It compiles (`:app:compileDebugAndroidTestKotlin`). It was not run (§7).

## 4. Protobuf wire neutrality

**Snapshot taken before the rename.** A field-table generator was added to
`desktop/proto/tests/namespace.rs` and run **on the pre-rename tree**, before any schema or crate was touched. It writes one line per wire fact: file, package, imports, `java_package`/outer class/multiple-files, every enum value and number, and for every message field its number, label, type, type name, oneof index and `proto3_optional`, plus oneofs and reserved ranges and names. The namespace root is written as `<root>`. The output became
`desktop/proto/tests/descriptor-field-table.txt`:

- 259 lines, **6 files, 117 fields**;
- SHA-256 `69ef09ccacdb6a732021426de7aeb1352d0c6ae5471ed7187e6c96fba6ceec2c`;
- 0 occurrences of `omnibridge`.

**After the rename,** `the_field_table_is_identical_to_the_pre_rename_snapshot` recomputes the table from the renamed schemas (root `pliwee`). It asserts 6 files and 117 fields (non-vacuous), then line-by-line equality, then whole-text equality. It passes. The snapshot is never regenerated by the test.

The Kotlin side agrees: `WireIdentityTest` observes `io.github.yurisismotto.pliwee.proto.Envelope`, and the built debug APK's dex references proto classes **only** under `io/github/yurisismotto/pliwee/proto/` (609 references, 0 under `omnibridge/proto/`). The cross-language envelope, pairing and notification KATs pass unchanged in both suites. The frozen DER vectors are unchanged (G3 B: `git diff --quiet 23a4503 -- protocol/testdata`).

## 5. The Windows portable job

The plan asks for two things: the job must still build exactly the seven portable crates, and its `-like` filter must match ≥ 1 line or fail. Both are now enforced in two places.

- **In the workflow:** after the forbidden-crate check, `$selected = $lines | Where-Object { $_ -like 'pliwee-*' }`. The job fails unless the distinct package names selected number **exactly 7**. That is stricter than the plan's "≥ 1": AGENTS.md says "more than zero is not a count".
- **In the test suite** (`core/tests/portable_boundary.rs`), because the Windows job cannot run here:
  - `the_windows_job_builds_exactly_the_portable_crates` reads the seven package names from the crates' own manifests. It requires the `POC-CORE-04`, `Full codegen` and `Dependency boundary` steps to name exactly that set with `-p`, and the presence list to name each one.
  - `the_windows_feature_filter_selects_every_portable_crate` requires exactly one `-like` filter, and requires its prefix to select all 7 names.
- **Mutation check:** the filter was set back to `'omnibridge-*'`. The second test **failed** with "the -like 'omnibridge-*' filter selects 0 of 7 portable packages". The file was restored and the test passed again (11/11).
- **Local measurement of the filter's input:**
  - command: `cargo tree --locked --no-default-features --target x86_64-pc-windows-msvc -e normal -p <the seven> --prefix none --format '{p} [{f}]'`, exactly as the job runs it;
  - 90 unique lines, of which **exactly 7** start `pliwee-`: `pliwee-capability-{battery,clipboard,files,notifications}`, `pliwee-control`, `pliwee-core`, `pliwee-proto`;
  - all 7 have an empty feature set `[]`, so none of `unix-fs`, `linux-backends`, `upower` or `linux-dbus` is on.
